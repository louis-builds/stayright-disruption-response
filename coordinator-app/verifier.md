## Task 1: 脚手架验证

- `npx expo start` 能起，模拟器/Expo Go 打开后能看到底部一级导航（案件/通话/通知/我的），无红屏报错。
- `tsconfig.json` 里 `strict: true`，代码里没有隐式/显式 `any`（抽查几个 `api.ts`/`types.ts`）。
- 目录结构符合 `开发规范.md` 分层：抽查一个 feature 模块确实有 `types.ts`/`api.ts`/hook/Screen 文件分开，视图组件里没有直接 `fetch`（必须经过 hook）。
- 登录成功后重新打开 App（不清缓存）不用重新登录（原生 Cookie 持久化生效即可，不要求 AsyncStorage 里能看到 Cookie 原文——那条路线技术上不可行，见 plan.md Task 1 的修正说明）；调用登出接口后再请求受保护接口应变回 401/403。
- 故意用一个受保护接口在未登录状态请求，验证 401/403 会被统一拦截并跳转登录页，不是让页面卡死或崩溃。
- 分页类型（`PagedResult<T>`）字段跟后端 `list`/`total`/`page`/`pageSize`/`totalPages` 对得上，随便接一个现有列表接口验证不用额外转换。
- `.env` 已在 `.gitignore` 里，`git status` 确认不会被提交。

## Task 2: 后端 Calls 模块验证

- `dotnet build` 通过，新迁移能正常 `dotnet ef database update`（或应用启动时自动迁移），`\d calls` `\d call_recordings` 能看到设计的字段。
- 用协调员账号调 `POST /api/cases/{caseId}/calls`（body 指定 guest 或 hotel）返回 201/200 且能查到一条 `Call` 记录，状态从 `connecting` 在几秒内（Mock 状态机）自动流转到 `completed`。
- 通话"结束"后几秒内 `CallRecording` 表出现对应记录，`ProcessingStatus` 从 `pending` 自动流转到 `done`，`TranscriptText` 非空（哪怕是规则生成的假文本），`AiSummary` 非空且是真的调用了 Gemini（不是写死的固定字符串——换一次通话内容，总结文本要不一样）。
- `GET /api/calls/mine` 只返回当前登录协调员本人发起的记录：用两个不同协调员账号分别发起呼叫，A 账号查不到 B 账号发起的通话。
- 未认证或非 coordinator 角色调用任一 Calls 接口返回 403，响应体符合 `开发规范.md` 2.2 节统一结构。
- 代码里 `ITelephonyProvider`/`IAsrProvider` 是独立接口，`MockTelephonyProvider`/Mock ASR 实现类跟接口分离，注释或 README 里写清楚了未来换真实 Twilio/ASR 时该改哪个文件，不用改调用方代码。

## Task 3: 登录页与权限引导页验证

- 用同一个协调员账号分别以用户名和邮箱两种方式在同一个登录框里登录成功。
- 用一个 guest 或 hotel 角色的账号尝试登录，被拒绝并看到"仅供协调员使用"一类的明确提示，不能进入 App 主界面。
- 密码输入框有显示/隐藏切换，点击能实际看到明文/密文切换。
- 勾选 remember me 后退出重新打开登录页，`identifier` 输入框里已经预填了上次的值（密码框不预填明文密码）。
- 首次启动权限引导页：拒绝麦克风权限后，App 没有卡死或反复弹出系统权限框，而是显示"去设置里手动开启"一类的兜底提示，且提示里的操作能跳到系统设置（或至少给出清晰路径说明）。

## Task 4: 案件队列页验证

- 待处理/我的待办/处理中/已结案/全部五个 Tab 切换后数据确实不同且跟 Web 端同一批数据源对得上（用同一个协调员账号在 Web 端和 App 上分别看，案件数量/内容一致）。
- 筛选（状态/优先级/中断类型）和搜索（客人/酒店/案件号任一关键词）都能正确收窄列表，不是摆设。
- 下拉刷新有明显的加载态反馈，刷新后数据确实重新拉取（可以用后端新插一条案件验证刷新后能看到）。
- 案件卡片上的「呼叫客户」「呼叫酒店」按钮点击后直接跳转呼叫中页面且真的调用了 Task 2 的发起呼叫接口（能在数据库里查到对应 `Call` 记录，`CalleeType` 跟点的按钮一致）。

## Task 5: 案件详情页验证

- 打开一个真实案件，基本信息（客人/酒店/中断类型/状态）跟 Web 端同一案件展示的信息一致。
- 在 coordinator 线程发一条消息，Web 端协调员工作台打开同一案件能看到这条消息（数据双向可见，不是 App 自己的孤立数据）。
- AI 对话线程是只读的（界面上没有能在这个线程发消息的输入框，或者有输入框但被禁用/隐藏）。
- 对一个真实转人工过的案件做"合理/不合理"复核，提交后再用 Web 端打开同一案件能看到复核结果（跟现有 escalation-review 接口打通）。
- 重订方案审核：能看到方案列表、选择并确认执行一个方案，案件状态相应变化（跟 Web 端 Options 流程行为一致）。
- 结案后案件状态变为已结案，Web 端和 App 队列页里这条案件都从"待处理"移到"已结案"分类。
- 该案件下的通话记录列表能看到之前发起过的呼叫记录，点开能跳转到对应录音详情页。

## Task 6: 呼叫中/通话结束页验证

- 发起呼叫后进入呼叫中页面，计时器从 0 开始走动；点静音/免提按钮有视觉状态切换（不要求真的接了硬件，UI 状态正确即可，因为通话是 Mock 的）。
- 点击结束通话后跳转到通话结束小结页，显示的时长跟呼叫中页面计时器停止时的数值一致。
- 小结页显示"录音正在处理中"，几秒后（Mock 处理完成）自动或手动刷新能跳转到录音详情页且内容不是空的。
- 故意让一次呼叫的 Mock 状态走向"未接通"分支（如果 Mock 状态机有多种结果），验证小结页显示对应结果且「重新呼叫」按钮点击后能重新发起一次新的呼叫。

## Task 7: 录音详情/通话记录/通知/设置/网络异常验证

- 录音详情页的播放器能播放、暂停、拖动进度条、切换倍速，播放位置和转文本高亮的时间戳大致同步（不要求精确到毫秒，能感知到联动即可）。
- AI 总结区域展示的内容确实是结构化的（不是把转录全文原样贴一遍）。
- 下载录音/分享转录文本的入口点击后有实际反馈（生成文件或调起系统分享面板，不是死链接）。
- 标记"已处理"后状态持久化：退出 App 重新打开，标记状态还在。
- 我的通话记录页只显示当前登录协调员本人的通话（同 Task 2 的验证口径），筛选/搜索有效。
- 通知中心里点一条通知能跳转到对应案件/录音详情页，未读有视觉标记，标记已读后角标数字对应减少。
- 设置页改通知开关后退出重开还生效（本地持久化）；改密码后用旧密码登录失败、新密码登录成功；登出后 `AsyncStorage` 里的会话信息清空且回到登录页。
- 断网状态下（关闭模拟器/真机网络）呼叫按钮和发消息按钮变灰且有明确提示，不会点了没反应也不报错；恢复网络后一条之前"上传失败"的录音（如果能模拟出这个场景）会自动重试上传成功。
